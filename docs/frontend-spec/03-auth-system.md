# FicHub Authentication & Authorization

## Overview

FicHub uses a **JWT + refresh token** system with **role-based** and **level-based** access control. Two parallel permission systems exist:

- **Roles** (legacy): 0=reader, 10=curator, 50=admin, 100=superadmin
- **Levels** (F7 progression): 0-100, unlocks features progressively

## Token System

### JWT (Access Token)
- **Algorithm:** HS256 (HMAC-SHA256)
- **Payload:** `{ sub: user_id, exp: timestamp, iat: timestamp }`
- **TTL:** 30 days
- **Header:** `Authorization: Bearer <token>`
- **Storage:** Client-side in-memory (Svelte store)

### Refresh Token
- **Type:** Opaque random string (32 bytes, hex-encoded)
- **TTL:** 365 days
- **Storage:** Stored in DB (`refresh_tokens` table)
- **Exchange:** `POST /api/auth/refresh` returns new JWT + new refresh token
- **Rotation:** Each refresh invalidates the old refresh token

### Token Lifecycle
```
Login/Register → { user, token (30d), refresh_token (365d) }
    ↓
Client stores token in memory, refresh_token in localStorage
    ↓
API calls use Authorization: Bearer <token>
    ↓
Token expires (30d) → client calls /api/auth/refresh with refresh_token
    ↓
New { token, refresh_token } issued, old refresh_token invalidated
    ↓
If refresh_token expired (365d) → user must re-login
```

## Registration

**Endpoint:** `POST /api/auth/register`

### Anti-Bot Measures (Defense-in-Depth)
1. **Honeypot field:** Hidden `website` field — bots fill it, humans don't
2. **Timing trap:** `form_opened_at` timestamp — form must be open >500ms before submit
3. **Fake success:** Bots get `{ err: 0, user: {...}, token: "fake..." }` — no account created
4. **Rate limiting:** 10 auth attempts/min/IP via Redis sliding window

### Registration Modes (F7 Feature Gating)
- **`open`** (default): Anyone can register
- **`invite`**: Requires valid invite code (generated by admins)
- **`application`**: Closed signup, requires admin approval

### Request Body
```json
{
  "username": "string (2-32 chars)",
  "password": "string (min 6 chars)",
  "email": "string (optional)",
  "website": "",
  "form_opened_at": "ISO timestamp"
}
```

### Response
```json
{
  "err": 0,
  "user": {
    "id": 123,
    "username": "reader42",
    "role": 0,
    "level": 0,
    "xp": 0,
    "rank": null,
    "reputation": 0,
    "locale": "en"
  },
  "token": "eyJ...",
  "refresh_token": "a1b2c3..."
}
```

## Login

**Endpoint:** `POST /api/auth/login`

### Request Body
```json
{
  "username": "string",
  "password": "string"
}
```

### Response
Same shape as registration. Failed logins are telemetry-logged for bot scoring.

## Token Refresh

**Endpoint:** `POST /api/auth/refresh`

### Request Body
```json
{
  "refresh_token": "string"
}
```

### Response
```json
{
  "err": 0,
  "user": { "id": 123, "username": "reader42", ... },
  "token": "new_jwt...",
  "refresh_token": "new_refresh..."
}
```

**Important:** Refresh re-fetches the user from DB. Role/level changes take effect immediately.

## Role Hierarchy

| Role | Level | Capabilities |
|------|-------|-------------|
| 0 | Reader | Browse, search, bookmark, rate, review, comment, forum post |
| 10 | Curator | + Tag management, content fixes, author merges, uploads |
| 50 | Admin | + User management, blacklists, moderation, bulk operations |
| 100 | Superadmin | + Everything, system config |

## Level-Based Feature Gating

The `level` field (0-100) controls progressive feature unlocks via the `features` table:

| Level | Unlocked Features |
|-------|------------------|
| 0 | Basic browsing, search |
| 5 | Bookmarks, ratings |
| 10 | Reviews, comments |
| 20 | Lists, shelves |
| 30 | Forum posting |
| 40 | Requests board |
| 50 | Curator tools (if role >= 10) |
| 60+ | Advanced features |

Features can be checked via:
- `GET /api/features/available` — returns features available to current user
- `GET /api/me/progression` — returns XP, level, next level requirements

## Frontend Auth State

The SvelteKit frontend manages auth state via a Svelte 5 rune-based store:

```typescript
// frontend/src/lib/stores/auth.svelte.ts
interface AuthState {
  isLoggedIn: boolean;
  user: { id, username, role, level, xp, rank, reputation, locale } | null;
  token: string | null;
}
```

### Token Attachment
All API calls include the JWT via the `request()` helper:

```typescript
// frontend/src/lib/api/social.ts
function request(path, options) {
  const token = getAuthToken(); // from Svelte store
  return fetch(path, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { 'Authorization': `Bearer ${token}` } : {}),
      ...options.headers,
    },
  });
}
```

### Auto-Refresh
The frontend automatically refreshes tokens before expiry:
- On app load: check if token is expired, refresh if refresh_token exists
- On 401 response: attempt refresh, retry request
- On refresh failure: clear auth state, redirect to login

## Permission Checking

### Backend
```rust
// Require authenticated user
async fn protected_endpoint(AuthUser(auth): AuthUser) -> Result<...> {
    let user_id = auth.user_id.ok_or((StatusCode::UNAUTHORIZED, "login required"))?;
    // ...
}

// Require curator level
async fn curator_endpoint(AuthUser(auth): AuthUser) -> Result<...> {
    if auth.level < 50 {
        return Err(AppError::Forbidden("curator access required"));
    }
    // ...
}

// Require admin
async fn admin_endpoint(AuthUser(auth): AuthUser) -> Result<...> {
    if auth.level < 100 {
        return Err(AppError::Forbidden("admin access required"));
    }
    // ...
}
```

### Frontend
```typescript
// Check role
if (auth.user?.role >= 10) { /* show curator tools */ }

// Check level
if (auth.user?.level >= 30) { /* show forum */ }

// Feature check
const features = await getAvailableFeatures();
if (features.includes('advanced_search')) { /* show it */ }
```

## Rate Limiting

All auth endpoints are rate-limited via Redis:
- **Window:** 1 minute sliding window
- **Limit:** 10 attempts per IP per window
- **Response:** `{ err: 429, msg: "rate limit exceeded" }`

## Password Security

- **Hashing:** bcrypt with default cost (10 rounds)
- **Minimum length:** 6 characters
- **Storage:** `password_hash` column in `users` table

## Logout

There is no server-side logout endpoint. The client simply:
1. Clears the JWT from memory
2. Clears the refresh_token from localStorage
3. Redirects to home

The old JWT remains valid until expiry. For immediate revocation, the user would need to change their password (invalidates all refresh tokens for that user).

## Anonymous Access

Anonymous users (no JWT) can:
- Browse all public content
- Search
- View fic details
- Read comments/reviews
- View leaderboards
- View trending
- Use blind-date

Anonymous users cannot:
- Bookmark, rate, review, comment
- Post in forum
- Access personalized recommendations
- Use requests board
- Access any `/api/me/*` endpoints
